# Phase 09 Concepts

Concept notes and debrief records for Phase 09 checkpoints, in the order you'd read them while working through the phase.

| Folder | Observable result |
| --- | --- |
| [entity-list-scope-filtering/](entity-list-scope-filtering/) | CP1: a new, workspace-scoped `GET /entities` (Redis), fail-closed with no saved workspace, demo ad-hoc bbox/unfiltered fallback -- kept separate from the existing unscoped `GET /entities/live` map-viewport query. Verified with 116 passing tests and a live manual run against the real dev server (France vs. New York scoping, fail-closed, demo fallback all confirmed against real Redis/Postgres state). |
| [entity-detail-alert-join/](entity-detail-alert-join/) | CP2: `GET /entities/:entity_id` joins Redis live state (no staleness cutoff -- a dark entity's last known state is the point) with its recent alert history (as primary entity or counterparty) from Postgres. Closes the by-id enumeration gap CP1's list-only scoping left open, fail-closed to `404`. Verified with 124 passing tests (8 new, including two route-mount-order regressions) and a live manual run against the real dev server. |
| [entity-position-history/](entity-position-history/) | CP3: `GET /entities/:entity_id/history` -- required time window, TimescaleDB position track for that window, capped independently of window width. Reuses CP2's by-id access check via a new shared `resolveOperatorEntityAccess` helper (CP2's own handler refactored onto it) instead of re-deriving the same authorization decision. Verified with 131 passing tests (7 new) and a live manual run including a real `EXPLAIN ANALYZE` proving index-scan/chunk-exclusion behavior. A post-review hardening pass across CP1-CP3 (see that concept's debrief) then fixed a real false-negative in the shared access check, hardened the `/entities/live` route split structurally, and deduplicated two more triplicated/duplicated query helpers. |
| [entity-relationship-graph/](entity-relationship-graph/) | CP4: `GET /entities/:entity_id/graph` -- the first Neo4j read in the API service (a new `neo4j.ts` driver, mirroring `db.ts`/`redis.ts`'s module-level-instance pattern). Returns the entity's 1-hop `PROXIMITY_EVENT`/`KNOWN_ASSOCIATE` neighborhood, gated by the same shared by-id access check, now used a third time. Caught and corrected a wrong assumption about the driver's Integer-wrapping behavior before shipping, verified by a direct probe against the real driver rather than trusting `cypher-shell`'s own display formatting. Verified with 137 passing tests (5 new, seeding real graph data) and a live manual run against the real dev server's actual pre-existing 7,262-edge graph. |
| [alert-detail-and-richer-filtering/](alert-detail-and-richer-filtering/) | CP5: `GET /alerts/:alert_id` (unrestricted by status, same fail-closed `matchesScope` rule as the list) plus two new optional `GET /alerts` query params (`status`, `entity_id`), both additive with the pre-CP5 default proven unchanged. The last backend checkpoint in this phase -- entirely inside the `alerts` table, no new datastore. Verified with 145 passing tests (8 new) and a live manual run confirming the unchanged-default guarantee against real seeded Postgres data. |
| [entity-detail-panel/](entity-detail-panel/) | FE-CP1: the first frontend checkpoint. A dockable Entity Detail widget (Overview tab only; History/Relationships tabs inert, later checkpoints), opened by clicking any entity_id in `AlertWidget`, one instance per entity. Discovered and fixed a real architectural gap before coding -- the codebase had no multi-instance widget support yet -- by extending the outer Dockview instance (already capable of it) and adding the codebase's first React context, justified by two real consumers (this checkpoint's click-through and FE-CP3's later graph-pivot). Verified with 38 passing tests (8 new) and a real headless-browser run against the live dashboard: two entities opened as two coexisting panels, a repeat click on the first focused it instead of duplicating, and the dark-entity render path was confirmed against real backend data. |
| [entity-history-track/](entity-history-track/) | FE-CP2: the History tab -- a window selector (defaulting to the opening alert's own `detected_at`, threaded through `WorkspacePanelContext`'s second real use of its context) plus a hand-rolled altitude-over-time SVG chart backed by `GET /entities/:entity_id/history`. The map-overlay track itself stays explicitly out of scope, its own follow-on. Fixed two real `react-hooks` lint catches (`set-state-in-effect`, `purity`) with a keyed-remount pattern rather than suppression. Verified with 43 passing tests (5 new) and two real headless-browser runs: the empty-window state against the dev database's actual (confirmed-empty) `position_history` table, then the chart-rendering path against manually-seeded real position data showing a correct climb/descent polyline. |
| [entity-relationship-pivot/](entity-relationship-pivot/) | FE-CP3: the Relationships tab -- a circular 1-hop graph (solid `PROXIMITY_EVENT`/dashed `KNOWN_ASSOCIATE` edges, native tooltips, capped at 12 rendered neighbors with an explicit "+N more" count) backed by `GET /entities/:entity_id/graph`, with the third real use of `WorkspacePanelContext` powering the graph-pivot: clicking a neighbor opens its own independent panel, anchored to that edge's own `last_seen_ms`. Applied FE-CP2's keyed-remount lesson from the start -- zero lint issues this time. Verified with 50 passing tests (7 new) and a real headless-browser run against the dev environment's actual 23-edge Neo4j graph: the 12-node cap and truncation count rendered correctly, and a neighbor click opened a second, independently-populated panel while the original stayed open. This completes Phase 09's frontend against the approved mockup; only the map-overlay track (FE-CP2's noted follow-on) remains unbuilt. |

Backend checkpoints CP1-CP5 and frontend checkpoints FE-CP1 through FE-CP3 are all complete. The map-overlay position track (noted as a follow-on in FE-CP2) is the only piece from the original mockup not yet built.
